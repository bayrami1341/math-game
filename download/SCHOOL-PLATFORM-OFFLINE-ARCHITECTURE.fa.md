## ۰. خلاصهٔ اجرایی

**مسئلهٔ مادر:** در شرایط جنگ و قطع اینترنت جهانی، ارتباط معلم ↔ دانش‌آموز و نظم روزانهٔ بچه‌ها (تکلیف، خواب/بیداری، عادت‌های درسی) به‌هم می‌ریزد. ابزارهای موجود یا ابری‌اند (با قطعی اینترنت می‌میرند) یا تک‌کاربره (معلم را در حلقه نمی‌گیرند).

**راه‌حل پیشنهادی:** یک پلتفرم **چندسطحیِ آفلاین-اول** که روی **یک دستگاه داخل شبکهٔ محلی مدرسه** اجرا می‌شود و چهار سطح دسترسی دارد:

```
مالک پلتفرم (شما، مشاور مدارس)
   └─ مدرسه (یا معلم خصوصی به‌عنوان «مدرسهٔ تک‌نفره»)
        └─ کلاس
             └─ دانش‌آموز
```

**سه پایهٔ ارزش:**
1. **دستیار معلم** (میراث مستقیم v9/v10.2): ماموریت، ایستگاه، گزارش — معلم در مرکزِ حلقه.
2. **سامانهٔ عادت و نظم** (ماژول جدید): تکالیف، ساعت خواب/بیداری، چک‌لیست‌ها — با همان DNA پداگوژیکِ «بدون جریمه».
3. **پنل‌های سلسله‌مراتبی**: مالک → مدرسه → معلم → دانش‌آموز، همه روی شبکهٔ لوکال، بدون هیچ وابستگی به اینترنت.

**اصل یک‌خطی:** *نرم‌افزار جای معلم را نمی‌گیرد؛ کابلِ ارتباطی معلم و دانش‌آموز است — و باید بدون اینترنت هم وصل بماند.*

## ۲. مسئله، محیط، ذی‌نفعان

### ۲.۱. محیط عملیاتی (جنگ)
- اینترنت جهانی معمولاً قطع است؛ **فقط شبکهٔ محلی (LAN)** در دسترس است.
- سخت‌افزار باید ارزان و در دسترس باشد: مینی‌PC، لپ‌تاپ قدیمی، یا Raspberry Pi.
- کاربرِ پنل‌ها معلم و مدیر مدرسه‌اند؛ نصب و نگهداری باید در حد «کپی فایل و دوبار کلیک» بماند.
- برق ناپایدار است → داده‌ها باید در برابر قطع ناگهانی سالم بمانند.

### ۲.۲. ذی‌نفعان و مدل تجاری
| ذی‌نفع | نقش | چیزی که می‌خواهد |
|---|---|---|
| **مالک پلتفرم (شما)** | مشاور مدارس؛ فروشندهٔ پلتفرم | مدیریت مدارس مشتری، لایسنس، گزارش سلامت استقرار |
| **مدیر مدرسه** | مشتریِ سازمانی | دادن دسترسی به معلمین و کلاس‌ها، دید کلی مدرسه |
| **معلم خصوصی** | مشتریِ فردی | همان قدرت مدیر+معلم برای کلاس خودش |
| **معلم کلاس** | کاربر اصلی پنل | ماموریت دادن، دیدن وضعیت، صبح‌خبر |
| **دانش‌آموز** | کاربر نهایی | بازی، ایستگاه، برد عادت — بدون فرم و لاگین سنگین |
| **والد** (فاز بعدی) | ناظر فقط-خواندنی | دیدن برد عادت فرزند |

### ۲.۳. تصمیم معماری کلیدی #۱ — «معلم خصوصی = مدرسهٔ تک‌نفره» 🔧
به‌جای دو مسیر جدا برای مدرسه و معلم خصوصی، معلم خصوصی یک **Tenant از نوع تک‌نفره** است: خودش مدیر مدرسهٔ خودش است + یک کلاس. نتیجه: فقط یک سلسله‌مراتب، فقط یک مجموعه پنل، و پنلِ مدیرِ مدرسه برای معلم خصوصی «به دیدِ ساده‌شده» رندر می‌شود. (کاهش نصفِ پیچیدگی RBAC)

## ۳. معماری کلان

```
┌─────────────────────────── مدرسه (یک دستگاه: مینی‌PC / لپ‌تاپ / رزبری) ───────────────────────────┐
│                                                                                                  │
│  ┌───────────────────── سرور Node.js تک‌فرآیندی (میراث server/* ریپو) ─────────────────────┐      │
│  │  http.js   → ثابت‌ها، mime، ایستا، گیت LAN (فقط رنج خصوصی)        [✅ میراث v6 + موج۲-الف] │      │
│  │  start.js  → چندمستأجری، --host، چاپ IPهای LAN                   [✅ الگو + 🔧 گسترش]      │      │
│  │  rbac.js   → «چه کسی، در اسکوپ کدام مدرسه/کلاس»                  [🔧 جدید]                │      │
│  │  service-* → auth / tenancy / missions / habits / reports        [🔧 تفکیک service.js]    │      │
│  │  store.js  → ذخیرهٔ فایلی اتومیک (صف وعده + tmp + rename + 0600)  [✅ میراث عیناً]          │      │
│  └──────────────────────────────────────────────────────────────────────────────────────────┘      │
│                                        │  HTTP فقط-LAN، same-origin                               │
│        ┌───────────────┬───────────────┼────────────────┬────────────────┐                        │
│   پنل مالک*        پنل مدرسه        پنل معلم          اپ دانش‌آموز      کارت عادت کاغذی            │
│   (دسکتاپ)        (دسکتاپ)        (موبایل+دسکتاپ)   (PWA لمسی/تبلت)   (QR + ورود معلم)           │
│                                                                                                  │
│  * پنل مالک معمولاً از بیرون مدرسه بازدید می‌کند (لپ‌تاپ مشاور) یا از اسنپ‌شات امضاشده تغذیه می‌شود │
└──────────────────────────────────────────────────────────────────────────────────────────────────┘
                                    │ (فقط وقتی اینترنت برگشت — اختیاری)
                              پل همگام‌سازی → ابرِ مالک (بکاپ/گزارش تجمیعی)
```

**سه تصمیم بنیادی:**

1. **یک سرور، یک فرآیند، چند سطح.** ✅ الگوی موجود (`server/http.js` فقط ۹۴ خط، `start.js` ۷۵ خط، `store.js` ۶۳ خط) نشان داده سرور صفر-وابستگی برای ۳۰–۴۰ کلاینتِ کلاس کافی است. پنل‌ها همه در همان فرآیند سرو می‌شوند؛ تفکیک سطح‌ها با RBAC نه با سرویس‌های جدا.
2. **کلاینت بدون فریم‌ورک و بدون هیچ منبع خارجی.** ✅ میراث `v9.html` (صفر منبع خارجی) و `src/v10` (جاوااسکریپت ماژولار خالص). دلیل: آپدیت با USB، ممیزیِ انسانیِ کد، بدون build toolchain. (🔧 پیشنهاد؛ در «تصمیم‌های باز» جایش است)
3. **داده روی دیسک، نه در رم.** ✅ الگوی `LocalStore` (نوشتن اتمیک با `tmp→rename` و پرم `0600`) مستقیماً برق‌ناپایداری و قطع ناگهانی را حل می‌کند.

## ۴. مدل دسترسی و امنیت (RBAC)

### ۴.۱. نقش‌ها
| نقش | اسکوپ | احراز هویت 🔧 |
|---|---|---|
| `owner` | همهٔ مدارس | نام‌کاربری+رمز (هش نمکی سرور-ساید)، جلسهٔ کوکی HttpOnly |
| `school_admin` | یک مدرسه | نام‌کاربری+رمز |

| `parent_view` (فاز بعدی) | فقط-خواندنی فرزند | کد دعوای یک‌بارمصرف |

### ۴.۲. قاعدهٔ طلایی اسکوپ‌بندی 🔧
> **هر کلید داده و هر عملیات API، از ابتدا با شناسهٔ مدرسه و کلاس پیشوندگذاری می‌شود.** هیچ کوئری بدون `schoolId` resolved از جلسهٔ کاربر اجرا نمی‌شود. عبور از مرز اسکوپ = 403 با لاگ ممیزی.

الگوی کلید در store (ادامهٔ سنت `prefix/` در LocalStore ✅):
```
school/{schoolId}
user/{userId}                        member/{classId}/{userId}
class/{schoolId}/{classId}           result/{classId}/{studentId}/{resultId}
mission/{classId}/{missionId}        habitlog/{classId}/{studentId}/{date}
homework/{classId}/{homeworkId}      report/{schoolId}/{week}
license/{schoolId}                   audit/{date}/{seq}
```

### ۴.۳. گیت شبکه ✅
میراث موج ۲-الف (کامیت `0527941`): bind پیش‌فرض `127.0.0.1`، opt-in با `--host` یا `MATH_GAME_HOST`، و در حالت LAN **فقط رنج‌های خصوصی** (192.168/10.x/172.16–31) پاس می‌گیرند؛ نام‌های عمومی حتی با opt-in → 403. این گیت عیناً به پلتفرم جدید منتقل می‌شود.

### ۴.۴. حریم خصوصی کودک 🔧
- فقط دادهٔ حداقلی: نام کوچک/نام‌نوشتاری، نه شماره ملی و آدرس.
- گزارش‌های مقایسه‌ای کلاس، ناشناس‌نما رندر می‌شوند (لقب/آواتار) مگر برای معلم همان کلاس.
- لاگ ممیزی append-only برای هر عملیات پنلی؛ صفحهٔ «شفافیت» در هر پنل: هر عدد گزارش، با یک کلیک به رکورد خام می‌رسد (اصل «گزارش بدون مسیر داده ممنوع»).

## ۵. پنل‌ها (چهار سطح رابط)

### P1 — پنل مالک (شما) 🔧
- ساخت/معلق‌کردن مدرسه، صدور **لایسنس آفلاین** (بند ۹)، تخصیص ظرفیت (صندلی).
- «سلامت استقرار»: از اسنپ‌شات امضاشدهٔ هر مدرسه (بند ۸.۴) — آخرین فعالیت هر کلاس، adoption واقعی.
- صفحهٔ شفافیت: رجِ کامل تغییرات هر مدرسه.

### P2 — پنل مدرسه 🔧
- ساخت کلاس‌ها، افزودن معلمین، تخصیص معلم↔کلاس.
- روشن/خاموش‌کردن ماژول‌ها (تمرین ضرب، عادت‌ها، تکلیف) برای کل مدرسه یا کلاس خاص.
- گزارش هفته‌ای مدرسه: کدام کلاس‌ها واقعاً استفاده می‌کنند (DAU کلاسی، نه فقط نصب).

### P3 — پنل معلم 🔧 (بذر: TEACHER_PANEL.md ✅)
ساختار صفحه‌ها مستقیماً از فلسفهٔ سند موجود ورثه می‌شود: پنج صفحهٔ اصلی با **«صفحهٔ امروز»** به‌عنوان خانه، سه لایهٔ افشا (نمای کلی → جزئیات → رکورد خام)، و اصل «هر عدد = یک در».
- ماموریت‌دادن (از بانک ماموریت‌های لایه‌بندی‌شدهٔ M1) + تکلیف غیردیجیتال (M3).
- «صبح‌خبر»: امروز چه کسی تمرین کرد؟ تکلیفِ دیروز چه شد؟ کدام زنجیرهٔ عادت در خطر است؟ (فقط هشدار، نه محکومیت.)
- ورود دستی/گروهی نتایج کارت عادت کاغذی.
- چاپ: کارت عادت هفتگی، برگهٔ گزارش والد.

### P4 — اپ دانش‌آموز 🔧 (بذر: src/v10/station ✅)
- UX ایستگاهِ لمسیِ موجود (انتخاب نام → PIN → کار) عیناً حفظ می‌شود.
- تب جدید: **برد عادت من** — تقویم ماهانه با ستاره‌ها (خواب/بیداری، تکلیف، چک‌لیست)، زنجیرهٔ زنده، بدون هیچ عدد تنبیهی.
- PWA نصب‌شدنی روی تبلت/موبایل کلاس؛ کش کامل با Service Worker (میراث آفلاین-اول ✅).

## ۶. ماژول‌های محصول

### M1 — هستهٔ تمرین (میراث مستقیم) ✅
بذر: `src/v10/*` (ایستگاه مستقلِ v10.2) + موتور لایه‌بندی سؤال و ماموریت جانبی. بانک سؤال‌ها per-layer از v10.2 (کامیت `52387ba`) منتقل می‌شود. هیچ Firebase‌ای در این مسیر نیست.

### M2 — دستیار معلم (میراث + تکمیل) ✅/🔧
ماموریت، ایستگاه، گزارش — از v9/v10.2. حلقهٔ ناقصِ فعلی (کد نتیجهٔ امضاشدهٔ HMAC، طرح ۲-ب/۲-پ موج ۲) در پلتفرم جدید به‌صورت native پیاده می‌شود: هر نتیجهٔ دانش‌آموز همیشه با HMAC امضا و در store ثبت می‌شود.

### M3 — سامانهٔ عادت و نظم (کاملاً جدید) 🔧 — قلب درخواست شما
| ابزار | سازوکار | پداگوژی |
|---|---|---|
| **تکالیف** | معلم تکلیف می‌دهد (دیجیتال: ماموریت M1 / غیردیجیتال: «روخوانی ۱۰ دقیقه»)؛ پنجرهٔ زمانی دارد نه ساعت دقیق؛ تیک‌زدن توسط دانش‌آموز یا معلم | تکمیل → ستاره؛ ندادن → هیچ جریمه‌ای جز «خالی‌ماندن خانهٔ تقویم» |
| **خواب/بیداری** | پنجرهٔ شبانه (مثلاً ۲۰:۳۰–۲۲:۰۰) با وقتِ سرور؛ ثبت «چراغ خاموش»؛ نمودار ماه | هشدار الگو فقط به معلم؛ بچه فقط ستاره می‌بیند |
| **چک‌لیست صبح/شب** | معلم per-class تعریف می‌کند (کیف چیدن، مسواک…)؛ تیک روزانه | کارت کوچکِ کامل‌شدنی، انیمیشن ملایم |
| **زنجیره (استریک)** | شمارش روزهای موفق هر عادت | زنجیرهٔ شکسته فقط «خانهٔ خالی» می‌شود — صفرِ تنبیهی ممنوع (قانون تطبیق بند ۱) |

**مسئلهٔ سختِ طراحی — عادت در خانه، سرور در مدرسه:** چون سرور فقط در LAN مدرسه زنده است، ثبت شبانه در خانه به سه راهِ صادقانه ممکن است (تصمیم پیش‌فرض: B، ارتقا: A):
- **A) گوشی دانش‌آموز/والد با PWA:** ثبت در خانه در IndexedDB ذخیره می‌شود (الگوی outbox میراث ✅) و با ورود دوباره به وای‌فای مدرسه، خودکار ACK می‌شود.
- **B) کارت عادت کاغذی (MVP):** کارت هفتگی چاپی با کد روز؛ در کلاس معلم گروهی وارد می‌کند. صفر وابستگی به دستگاه.
- **C) تبلت کلاس:** فقط ثبت در مدرسه؛ خانه از تصویر ذهنی کارت چاپی استفاده می‌کند.

ساعتِ سرور = تنها منبع حقیقتِ زمان (کلیتِ پنجره‌ها سمت سرور سنجیده می‌شود؛ خطای ساعتِ دستگاه بی‌اثر است). منطقهٔ زمانی per-school قابل تنظیم.

### M4 — گزارش‌ها 🔧
- معلم: امروز / هفته / پروندهٔ تک‌دانش‌آموز (تمرین + عادت در یک نگاه) — هر عدد clickable به رکورد خام.
- مدرسه: مقایسهٔ کلاس‌ها، adoption.
- مالک: سلامت استقرار از اسنپ‌شات (بند ۸.۴).

### M5 — پل همگام‌سازی پس از بازگشت اینترنت (اختیاری، هرگز الزامی) 🔧
هیچ قابلیتی به این ماژول وابسته نیست. وقتی اینترنت برگشت: اسنپ‌شات امضاشده (HMAC) از مدرسه به ابر مالک می‌رود (بکاپ + گزارش تجمیعی)، یا پل دوطرفهٔ سبک برای به‌روزرسانی محتوای بانک سؤال.

## ۸. جریان‌های داده

### ۸.۱. تمرین در کلاس (روزانه) ✅ الگو
دانش‌آموز → تبلت ایستگاه (PWA کش‌شده) → عملیات HTTP به سرور LAN → Result با HMAC ثبت → پنل معلم همان لحظه می‌بیند. بدون اینترنت، چون همه‌چیز same-origin روی LAN است. قطع برق → نوشتن اتمیک store → هیچ رکوردی نمی‌سوزد.

### ۸.۲. عادت شبانه (خانه) 🔧
گزینهٔ B پیش‌فرض: کارت کاغذی → صبح در کلاس معلم گروهی وارد می‌کند (`source: paper`).
گزینهٔ A: PWA خانه → نوشتن در IndexedDB با outbox (backoff نمایی + ACK ✅ میراث) → وقتی دستگاه دوباره در LAN مدرسه دید، فلش می‌کند.

### ۸.۳. سلسله‌مراتبِ راه‌اندازی (onboarding) 🔧
مالک مدرسه را می‌سازد و لایسنس صادر می‌کند → مدیر مدرسه کلاس و معلمین را می‌سازد → معلم فهرست دانش‌آموزان را وارد می‌کند (چسباندن فهرست نام، یا CSV ساده) → هر دانش‌آموز PIN می‌گیرد → اولین تمرین همان روز.

### ۸.۴. اسنپ‌شات برای مالک 🔧
دکمهٔ «بستهٔ مشاور» در پنل مدرسه → JSON امضاشدهٔ HMAC (آمار استفاده، بدون دادهٔ حساس کودک) → فلش/ایمیل بعد از اتصال → پنل مالک می‌خواند. مالک می‌تواند با لپ‌تاپش به LAN مدرسه وصل شود و مستقیم پنل مالکِ همان دستگاه را ببیند (پنل مالک روی دستگاه مدرسه هم هست، فقط با نقش owner).

## ۹. لایسنس آفلاین و مدل تجاری 🔧
- لایسنس = JSON امضاشده (HMAC با کلید مالک): `{school, seats, expiresAt}` — سرور مدرسه بدون هیچ تماسی آن را verify می‌کند (الگوی HMAC موجود در service.js ✅).
- انقضا → **هرگز داده‌ها را قفل نمی‌کند**؛ فقط پنل‌ها به حالت فقط-خواندنی با پیام تمدید می‌روند (اخلاق حرفه‌ای + اعتمادِ مشتری).
- صندلی = Membership فعال؛ افزایش صندلی = صدور لایسنس جدید.

## ۱۰. استقرار و عملیات 🔧
1. نصب: کپی پوشه از USB → `npm ci --ignore-scripts` → اجرای اسکریپت شروع (میراث ✅).
2. شبکه: `--host 0.0.0.0` برای وای‌فای کلاس + راهنمای فایروال چاپ‌شده (میراث موج ۲-الف ✅).
3. آپدیت: بستهٔ USB با شمارهٔ نسخه + مانیفست امضاشده؛ سرور قبل از اعمال، hash چک می‌کند.
4. بکاپ: کپی شبانهٔ خودکار فایل داده به USB درج‌شده + دکمهٔ «خروجی پشتیبان» در پنل مدرسه؛ بازگردانی با wizard.
5. ساعت: همگام دستیِ ساعت سرور در نصب (بدون NTP)؛ نمایش ساعت سرور در همهٔ پنل‌ها.

## ۱۳. ریسک‌ها و تصمیم‌های باز

**ریسک‌ها:**
- **تورم دامنه:** وسوسهٔ ساختن «سیستم کامل اداری مدرسه» (کارنامه، حضوروغیاب رسمی…) → خط قرمز پیشنهادی: هر قابلیت باید یا به تعامل معلم↔دانش‌آموز یا به نظمِ روزانهٔ دانش‌آموز گره بخورد، وگرنه out-of-scope.
- **نقطهٔ شکستِ واحد:** خرابی دستگاه مدرسه → تخفیف با بکاپ USB روزانه + نصب روی دستگاه دوم در ۱۰ دقیقه.
- **وای‌فای شلوغ کلاس:** ۳۰+ دستگاه → polling سبک و payload کوچک (الگوی v9 ✅)؛ WebSocket فقط اگر روزی واقعاً لازم شد.
- **پذیرش معلم:** اگر صبح‌خبر هر روز «لیست تقصیر» باشد، معلم رها می‌کند → قانون: هشدار بدون برچسب قضاوت، همیشه با «اقدام پیشنهادی».

**تصمیم‌های باز (نیازمند فرمان شما):**
1. نام رسمی پلتفرم («کارگاهِ مدرسه» فقط عنوان کاری است).
2. کلاینت: ادامهٔ vanilla JS (پیشنهاد من، به‌دلیل ممیزی‌پذیری و آپدیت USB) یا فریم‌ورک؟
3. لایسنس: سالانه یا صندلی‌محور؟
4. والدین: فقط-خواندنی از فاز ۲ یا ۴؟
5. M1 فقط ضرب بماند یا فاز ۳ درس دوم (فارسی/علوم) اضافه شود؟
