# گزارش بررسی و اعمال فاز یک نسخهٔ ۹

تاریخ: ۲۰۲۶/۱۰/۱۶ — قرارداد: `9.0.1-phase1` — اصلاح اسکما: `1.0.1`.

## نتیجه و دامنه

سه فایل ارسالی مالک محصول، مبنای این تحویل‌اند. تصمیم‌های قفل‌شده حفظ شده‌اند: ورود معلم با `firebase_email_link`، API مورد اعتماد با `cloud_functions_or_equivalent`، پذیرش هر دو عضویت `pending` و `active` و خاموش‌بودن پیش‌فرض رتبه‌بندی.

این فاز قرارداد و ابزار آزمون آن را منتشر می‌کند. کد بازی ۸.۱، تنظیمات Firebase، صورتحساب، قوانین محیط تولید و روش ورود فعلی تغییر نمی‌کنند. این موارد در فازهای اجرایی بعدی بررسی و اعمال می‌شوند.

## اصلاح‌های انجام‌شده روی فایل‌های ارسالی

| مورد | اصلاح |
|---|---|
| وضعیت متناقض قرارداد و فایل قفل | قرارداد به وضعیت قفل‌شده رسید و چک‌لیست تأیید هماهنگ شد |
| شناسه‌های نمونه کوتاه‌تر از `minLength: 8` | نمونه‌های requestId و eventId با شناسهٔ نمایشی سازگار جایگزین شدند |
| اسکمای نمونه با کلید سفارشی `operations` | انواع اجرایی به `$defs` استاندارد منتقل شدند و ریشه به آن‌ها ارجاع می‌دهد |
| نبود `type: object` در درخواست‌ها | ورودی‌های غیرشیء صریحاً رد می‌شوند |
| ورود فیلدهای نامرتبط یا جعلی | درخواست‌ها و پاسخ‌ها فقط فیلدهای مستند را می‌پذیرند |
| نبود اسکمای پاسخ | پاسخ موفق پنج عملیات، رسید و پاسخ خطا تعریف شدند |
| هدف جلسه صرفاً یک شیء نامشخص بود | شکل مستند `sector` با sectorId مثبت قابل آزمون شد |
| مرجع فایل‌های خارج از مسیر یا ناموجود | پیوندهای نسبی اسناد و اسکما اصلاح شدند |

نسخهٔ قرارداد و تصمیم‌های عملیاتی تغییر نکرده‌اند. `artifactRevision: 1.0.1` تکمیل و سخت‌گیری اعتبارسنجی نمونه‌های ارسالی را ثبت می‌کند. هیچ هدف آموزشی جدید، عملیات جدید یا روش احراز هویت دیگری در این اصلاح معرفی نشده است.

## اعتبارسنجی

ابزارهای Ajv و ajv-formats فقط وابستگی توسعه‌اند. نسخه‌های دقیق و درخت وابستگی در package-lock.json ثبت می‌شوند. نصب با اسکریپت‌های بسته‌ها خاموش انجام می‌شود:

```bash
npm ci --ignore-scripts
npm run test:contracts
npm test
```

آزمون قرارداد، اسکمای Draft 2020-12 را در حالت سخت‌گیرانه کامپایل و همهٔ نمونه‌های JSON قرارداد را با مرجع همان عملیات بررسی می‌کند. ورودی‌های جعلی، نوع اشتباه، نسخهٔ نامعتبر، زمان نامعتبر، رسید ناقص و افشای عضو دیگر در پاسخ عضویت باید رد شوند. اعتبارسنج نباید ورودی را تغییر دهد یا به‌جای سرور پیش‌فرض اعمال کند.

آزمون‌های قبلی تسلط و لیدربرد همچنان اجرا می‌شوند. نتیجهٔ اجرای محلی با Node v24.19.0: **۱۷ آزمون تسلط + ۱۸ آزمون لیدربرد + ۳۱ آزمون قرارداد = ۶۶ موفق، بدون شکست**. هر ۱۱ نمونهٔ JSON درخواست و پاسخ در سند قرارداد نیز بررسی شده‌اند.

## مواردی که آزمون شکل JSON ثابت نمی‌کند

- اصالت هویت، مالکیت کلاس و فعال‌بودن عضویت؛
- تصادفی و امن بودن توکن، انقضا و سقف مصرف آن؛
- محدودیت نرخ، جلوگیری از حدس کد و هزینهٔ سوءاستفاده؛
- اثر یک‌باره، تراکنش‌ها، رقابت دو دستگاه و سازگاری گزارش؛
- صحت نتیجهٔ آموزشی، اعتمادپذیری زمان مشتری و ثبت در دیتابیس؛
- امنیت قوانین Firebase یا موفقیت ورود ایمیلی در شبکهٔ واقعی مخاطب.

این موارد آزمون سرور، قواعد و پذیرش مستقل لازم دارند. فایل JSON Schema و سبزبودن آزمون‌های آن به معنی آماده‌بودن API تولید نیست.

## تکمیل لازم پیش از پذیرش پاسخ در سرور

فاز دو می‌تواند روی هستهٔ خالص آغاز شود. پیش از فاز پذیرش پاسخ، جزئیات زیر باید در قرارداد اجرایی بعدی با نسخهٔ صریح تکمیل شوند:

1. معنای رسید هر پاسخ در یک بستهٔ دارای خطا: بستهٔ اتمی یا پذیرش جزئی، و نحوهٔ گزارش پاسخ‌های ردشده.
2. دامنهٔ یکتایی requestId و eventId، مقایسهٔ محتوای تکراری، مدت نگهداری رسید و رفتار تعارض درخواست.
3. امضای کامل finalizeSession، getSyncStatus و grantDeviceAccess؛ در فایل ارسالی فقط شرح کوتاه دارند.
4. عملیات تأیید یا لغو عضویت pending و انتقال نویسندهٔ جلسه؛ این‌ها در پنج عملیات فعلی پیاده‌سازی یا کامل تعریف نشده‌اند.
5. سقف اندازه و تعداد پاسخ در بسته، طول و دامنهٔ شناسه‌ها، عمر دعوت، سقف مصرف و قواعد پاک‌سازی.
6. انتخاب لایهٔ انتقال و شیوهٔ توکن هویت، خطاهای انتقال و محدودیت‌های استقرار و صورتحساب.

این موارد به‌صورت فرض پنهان در کد بازی یا سرور آینده وارد نمی‌شوند. اجرای فاز یک شامل شروع فاز دو یا استقرار سرور نیست.
